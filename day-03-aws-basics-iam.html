AWS Basics and IAM

How AWS is laid out, the three ways to drive it, and then the first real service: who is allowed to do what, and how AWS decides.

Day 03 · AWS Basics Cloud Adoption Framework Console, CLI, SDK IAM Policies

What to remember

IAM is the largest single topic in Domain 1, which is itself 30% of the exam. These five are the ones that decide questions.

  1. Explicit deny always wins. One deny anywhere in any applicable policy sinks the whole request, no matter how many allows exist. → 09
  2. Everything is denied by default. No matching allow means implicit deny, so a permission has to be granted somewhere before it exists at all. → 09
  3. Roles are assumed, not logged into. They hand out temporary credentials and have no password or access key. This is the right answer whenever something needs access to something else. → 07
  4. IAM is global. Users, groups, roles and policies are not per-Region. → 05
  5. The root user is for a short list of tasks and nothing else. Secure it, then leave it alone. → 10

01 Regions, zones and edges

Three levels of geography, and choosing between them is a real architectural decision.

The three levels
LevelWhat it isChosen for
RegionA geographic area such as us-east-2 (Ohio). Contains at least three Availability Zones.Latency to users, data-residency law, service availability, and price — which differs by Region.
Availability ZoneOne or more discrete data centres inside a Region, with independent power, cooling and networking.Surviving a failure. Run across at least two.
Edge locationA much larger set of smaller sites used for caching and DNS, not for running your servers.Getting content physically close to users. CloudFront and Route 53 live here.
Note Four things to weigh when picking a Region

Compliance first, because it can be non-negotiable — some data legally cannot leave a country. Then latency to your users, then price, then service availability, since new services do not launch everywhere at once.

02 The Cloud Adoption Framework

AWS's checklist for moving an organisation to the cloud. It is about people and process, not architecture.

The point of the CAF is that the technical migration is the easy half. It groups the work into six perspectives, each owned by a different group of people.

Good news This one was missed in class

The class notes record CAF as missed, so this section is written from AWS's own framework page rather than from the lecture. For SAA-C03 the CAF is background: know the six perspective names and that the framework exists. It is examined far more heavily on the Cloud Practitioner paper.

Caution Do not confuse it with Well-Architected

Two different frameworks. CAF is about adopting the cloud as an organisation — people, governance, process. Well-Architected is about designing a workload, and its six pillars are what SAA-C03 is actually built on.

04 Three ways to talk to AWS

All three hit the same API. The Console is just a website that makes the calls for you.

Point and click Management Console

  • A web interface, per-Region in most services
  • Best for learning, exploring and one-off tasks
  • Not repeatable, and leaves no record of intent

Type commands CLI

  • aws s3 ls, and several thousand others
  • Scriptable, so it can go in automation
  • Needs credentials configured, usually an access key or a role

From code SDKs

  • Libraries for Python (boto3), JavaScript, Java, Go and more
  • How an application talks to AWS from inside itself
  • Picks up credentials the same way the CLI does
Note The Console is not special

Every click makes the same API call the CLI would. This matters for two reasons: CloudTrail records all of it identically, and an IAM policy that denies an action denies it in the Console too. There is no back door through the web interface.

05 What IAM is

Identity and Access Management controls who can do what to which resource. It is free, and it is global.

Note Global, not regional

Users, groups, roles and policies are not tied to a Region. Create a user once and it exists everywhere. This is unusual — most services are regional — and the exam likes testing it.

Authentication is not authorization

Two separate steps that happen in order, and mixing them up makes policy behaviour impossible to reason about.

The two steps
 AuthenticationAuthorization
QuestionWho are you?What are you allowed to do?
DefinitionVerifying an identity before granting access to a system, account or file.Verifying the level of access that identity has.
PurposeConfirm the identity and keep out impostors.Make sure people reach only what they should.
ProcessCompare supplied credentials against stored ones.Grant or deny based on policies attached to the identity.
MethodsPassword, access key, MFA codeIAM policies
Fails asCannot sign in at allSigned in, but AccessDenied

A useful test: an AccessDenied error means authentication already succeeded. AWS knows exactly who you are; it has decided you may not do this.

06 The vocabulary

Four words AWS uses precisely and most material uses loosely. Worth ten minutes now to save confusion later.

Four terms
TermMeansExamples
ResourceAn object stored in a service, the thing being acted upon.An S3 bucket, an EC2 instance, and also an IAM user — users are resources too.
IdentityThe parts of IAM that can be given permissions and be identified.Users, groups, roles.
EntityThe parts AWS uses to authenticate with — the things that can actually sign in or be assumed.Users and roles. Not groups, because a group cannot authenticate.
PrincipalThe person or application making the request, using an entity.A human signed in as a user, an application that assumed a role, the root user.
Good news The distinction in one sentence

A group is an identity but not an entity — you can attach permissions to it, but nobody can log in as it. Everything else in IAM is both. That single exception is the whole reason AWS bothers to keep the two words apart.

And principal is not a fourth kind of object at all. It is the role being played in a particular request: whoever is making this call, right now, through some entity.

Federation

The class notes have "federated something?" with a question mark, so: federation means trusting an outside identity provider rather than creating IAM users.

Your staff already have accounts somewhere — Google Workspace, Microsoft Entra, Okta, an on-premises Active Directory. Federation lets them sign in there, and AWS accepts that provider's word for who they are, handing back temporary credentials. No second password, no IAM user to create and later forget to delete.

Caution This is the modern default

AWS now recommends federated access through IAM Identity Center over creating individual IAM users for humans. If an exam question describes a company with an existing corporate directory wanting AWS access, the answer is federation — not "create IAM users for everyone".

07 Users, groups and roles

Three identities. The exam mostly wants to know when the answer is a role.

Long-lived IAM user

  • A permanent identity for one person or one application
  • Has a password, access keys, or both
  • Credentials last until someone rotates them

A container IAM group

  • A collection of users, for attaching policies once
  • Cannot be nested — no group inside a group
  • Cannot be signed in as; it is not an entity

Temporary IAM role

  • Assumed, not logged into
  • No password and no access key
  • Hands out short-lived credentials that expire on their own
Danger Never put access keys on an EC2 instance

The wrong way to let an instance reach S3 is to create an IAM user, generate an access key, and write it into a config file on the box. That key is long-lived, sits on disk, gets committed to Git, and survives the instance.

The right way is an IAM role attached to the instance. Credentials are delivered automatically, rotate themselves, and expire. When a question asks how one AWS thing should access another AWS thing, the answer is a role — nearly every time.

When each is used
SituationUse
A person needs console accessFederation through IAM Identity Center, or an IAM user if there is no directory
Twelve developers need the same permissionsA group, with one policy attached to it
An EC2 instance needs to read S3A role attached to the instance
A Lambda function needs DynamoDBThe function's execution role
Another AWS account needs accessA role that trusts that account
A user needs admin rights occasionallyA role they assume when needed, then drop

08 Policies

A policy is the rule book: a JSON document saying which actions are allowed or denied on which resources.

Two kinds, by where they attach

Where a policy attaches
 Identity-basedResource-based
Attached toA user, group or roleThe resource itself, such as an S3 bucket
Answers"What may this identity do?""Who may touch this thing?"
Principal elementNot used — the identity it is attached to is impliedRequired, because it must name who is being trusted
Managed or inlineBoth. AWS managed, customer managed, or inlineInline only, and only on services that support them
Cross-accountNeeds a role to be assumedCan grant access directly to another account

The shape of a policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadTheReportsBucket",        // optional label
      "Effect": "Allow",                    // Allow or Deny
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": "arn:aws:s3:::reports/*",  // which thing
      "Condition": {                        // optional, and powerful
        "IpAddress": { "aws:SourceIp": "203.0.113.0/24" }
      }
    }
  ]
}
The elements
ElementDoes
VersionThe policy language version. Always 2012-10-17; it is not a date you choose.
StatementA list of rules. A policy can hold several.
SidAn optional label, purely for humans.
EffectAllow or Deny.
ActionThe API calls, as service:Operation. Wildcards allowed.
ResourceWhich resources, by ARN.
PrincipalWho is being granted access. Resource-based policies only.
ConditionExtra tests — source IP, MFA present, time of day, a tag's value.
Note An ARN names everything

Every resource in AWS has an Amazon Resource Name, shaped arn:aws:service:region:account:resource. Globals like S3 and IAM leave the region and sometimes the account empty, which is why an S3 ARN has the run of colons: arn:aws:s3:::bucket-name.

09 How a request is decided

Learn this flow and a whole class of exam questions becomes mechanical.

The three outcomes
OutcomeHappens whenBeats
Explicit denyAny applicable policy says "Effect": "Deny"Everything. Nothing overrides it.
Explicit allowSome policy says Allow and nothing deniesThe default deny
Implicit denyNothing mentions the action at allNothing. It is the default state.
Danger Two rules that answer most questions

One deny sinks it. A user can have ten policies allowing an action; a single deny in any one of them, or in a permissions boundary or an Organizations control policy, and the request fails. There is no counting and no majority.

Silence is refusal. Permissions do not exist until granted. "The policy does not mention S3" means no S3 access, not unrestricted S3 access.

Note Explicit deny versus implicit deny

Both end in refusal, so why two names? Because an implicit deny can be overturned by adding an allow somewhere, while an explicit deny cannot be — the deny has to be removed. That is exactly what makes explicit deny the tool for guardrails you do not want anyone overriding.

10 Securing the account

A short list of practices, and one account you should almost never sign in as.

Least privilege

Grant the minimum permissions needed for the task, and no more. Start from nothing and add, rather than starting from administrator and trimming. It is easier to grant a missing permission later than to discover an unnecessary one after it has been used.

Multi-factor authentication

A password is one factor: something you know. MFA adds something you have — a phone app, a hardware key. A stolen password alone then buys the attacker nothing.

Good news Root MFA is now enforced by default

AWS now requires MFA on the root user, prompting at account creation or sign-in. Older study material says "remember to turn on root MFA" as though it were optional. Turn it on for privileged IAM users too, where it is still your responsibility.

The rest of the checklist

  • Rotate access keys regularly, and delete ones nobody uses. Better still, use roles so there are no long-lived keys to rotate.
  • Turn on CloudTrail so every API call is recorded. Without it there is no answer to "who deleted that".
  • Use AWS Organizations to separate environments into accounts and apply service control policies across them.
  • Prefer roles over users wherever something is not a human being.

The root user

The root user is the email address the account was created with. It has unlimited power, cannot be restricted by IAM policy, and should be locked away.

Root against IAM user
 Root userIAM user
CreatedAutomatically, with the accountBy you, afterwards
Signs in withAccount email addressAccount ID plus username
PermissionsEverything, alwaysOnly what policies grant
Can be restrictedNo. IAM policies do not constrain it.Yes
Should be usedAlmost neverFor day-to-day work

What only the root user can do

A short list. Everything else belongs to an IAM identity.

  • Change the account email address, root password, or root access keys
  • Close the AWS account
  • Restore IAM permissions if an administrator locks everyone out
  • Turn on IAM access to the Billing and Cost Management console, and some billing tasks
  • Sign up for AWS GovCloud (US)
  • Register as a seller in the Reserved Instance Marketplace
  • Enable MFA Delete on an S3 bucket
  • Fix an S3 bucket policy or SQS queue policy that has locked out every principal
Caution One item in the class notes is not on AWS's current list

The notes list changing the support plan as root-only. It is widely repeated, but AWS's current documented list of root-only tasks does not include it. The items above are taken from that list — worth trusting over older material, including mine.

Protecting it

  • Enable MFA, ideally a hardware key rather than a phone.
  • Delete any root access keys. There is no good reason for the root user to have programmatic access.
  • Use an email address a team can reach, not one person's — people leave.
  • Create an admin IAM identity for real work on day one, and stop using root.
  • Alarm on root sign-in through CloudTrail, so any use is noticed.
